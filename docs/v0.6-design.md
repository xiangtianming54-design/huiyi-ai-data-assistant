# v0.6 设计：混合检索 + 会话摘要压缩

日期：2026-10-16  
状态：已发布（v0.6.0）

## 意图

现有知识问答只靠向量 Top-5，问法与文档用词不一致时容易漏检。多轮改写只取最近 6 条且整段塞进 Prompt，会话一长就又贵又不稳。

这一轮补两块短板，不改意图路由、不引入 Tool Calling：

1. **知识库检索**改为向量 + 关键词混合，再融合出给 RAG 的 Top-K。
2. **会话改写**保留近 10 轮原文；更早的轮次用 LLM 写成摘要并持久化，和近 10 轮一起参与改写。

## 目标

- 专有名词、短问、和文档用词不一致的问题，比纯向量更容易命中正确分块。
- 超过 10 轮的追问仍能改写指代，且不再把全部历史原文送进改写 Prompt。
- 无命中时的确定性兜底、引用按文件去重、知识/数据分流，行为与现在一致。
- 混合检索对 Java 仍是一次 search 调用；意图示例句 collection 不受影响。

## 非目标

- Agent / Tool Calling、知识库权限隔离。
- Cross-encoder 重排序模型（本轮融合用 RRF，不加第二套模型）。
- 会话摘要展示在前端。
- 改分块参数（仍是 500 / 50）。
- 按 token 精确裁剪（用「轮」和摘要，不用 tokenizer）。

## 反目标

- 为了混合检索把无关片段塞进 Prompt，导致模型编口径。
- 摘要失败就打断主问答。
- 意图分类（`intent_examples`）被关键词检索带偏。

## 约束

- 继续 Java 主编排 + Python Sidecar。
- 知识库向量仍在 Chroma；关键词索引必须与 upsert / delete 同步。
- 会话仍落 MySQL `chat_messages`。
- 摘要是额外一次 LLM 调用，失败必须降级，不能拖垮改写和主链路。

---

## 一、混合检索

### 范围

仅默认知识库 collection `huiyi_knowledge` 走混合检索。  
`intent_examples` 以及其它非知识库 collection **仍只做向量检索**。

### 关键词检索

- 对已入库分块正文建 BM25，中文按字符 bigram 或同等分词。
- 与 Chroma 同步：upsert 覆盖，按文件名删除时一起删。
- 落盘，进程重启后还在。不引入 Elasticsearch。

### 融合（RRF）

两条支路各取 `top_k * 2`（默认各 10 条）：

1. **向量**：cosine ≥ 0.5 才进入融合。
2. **关键词**：BM25 > 0 且至少命中一个查询词。

```text
RRF(d) = Σ 1 / (60 + rank_i(d))
```

按 RRF 取最终 Top-5。Java 侧对混合结果 **不再用 0.5 一刀切**（否则只靠关键词捞回的块会被滤掉）。列表为空才走「未找到足够信息」。

向量服务挂了：整次失败，降级话术。关键词索引空：退回纯向量。

接口仍是 `POST /api/vector/search`，按 collection 名决定走不走混合。

---

## 二、近 10 轮 + LLM 摘要

**一轮** = 一条用户 + 一条助手。近 10 轮 ≈ 最近 20 条原文。当前正在改写的这一问还不在库里，不计入。

超过 10 轮后，更早的消息由 LLM 压成一段中文摘要（约 400 字），和近 10 轮一起进改写：

```text
【更早对话摘要】
{summary}
【最近对话】
用户: …
助手: …
```

新 Prompt：`prompts/history-summarize.md`。已有摘要 + 新溢出的旧消息，增量再压，不每次重压全部历史。

新表 `chat_session_summaries`：`session_id`、`summary`、`covered_until_id`、`updated_at`。需要可重复执行的 ALTER，不能只改 init 脚本。

摘要失败：只用近 10 轮原文，主问答继续。不足 10 轮：不调摘要。前端不展示摘要。

---

## 验收

1. 用词和文档不完全一致时，混合检索仍能引用正确文件。
2. 超过 10 轮后，改写只带摘要 + 约 20 条原文；「那第二名呢？」仍能补全。
3. 摘要 LLM 失败时接口仍 200。
4. 删除知识库文件后，向量和关键词都检索不到。
