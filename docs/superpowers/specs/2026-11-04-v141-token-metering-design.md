## 1. 要做什么

每个人有自己的每日 Token 额度。额度由用户等级决定。聊天页能看见今天还剩百分之多少。开跑前不够用时，这一问不开始，并可以申请当天加 50 万。加完的额度到晚上 12 点失效。这一问已经开始后，让它说完，结束再记账。下一句才拦住。

它不是：

- 改 v1.4.0 的备份、压测、告警、发布验收；
- 每天提问次数上限；
- 按等级区分的每秒次数；
- 把工作区角色 `OWNER` / `ADMIN` / `EDITOR` / `VIEWER` 当成一级、二级、三级；
- 用户自己申请升级，或把已经注册的第一级改成更高一级；
- 多个第二级、多租户。以后多租户时，第二级是老板，第一级是他的员工。本版只有一个第二级。
- 充值。第二级向第三级提额，以后可以改成充值，本版不做支付。

## 2. 用户等级

等级是用户自己的属性，和所在工作区的成员角色分开。

| 等级 | 名称 | 每天 Token | 谁能成为 |
| --- | --- | --- | --- |
| 1 | 第一级 | 50 万 | 自己注册。注册成功就是第一级 |
| 2 | 第二级 | 150 万 | 只能由第三级新建账号，再交给员工 |
| 3 | 第三级 | 500 万 | 只能由第三级新建账号。第一个是已经存在的 `blank` |

已拍板的账号：

- `blank`（用户编号 16）是第一个第三级。等级列加上时补记，不是事后把一个第一级改上去。
- `limit`（用户编号 17）是本版唯一的第二级。同样在等级列加上时补记。
- 这两人目前都是工作区 1 的 `VIEWER`。补记等级不改他们的工作区角色。
- 除这两人以外，等级列出现时已经存在的用户记为第一级。

不能做的事：

- 第一级不能申请升级。
- 不能把一个已经是第一级的用户改成第二级或第三级。
- 第二级不能新建账号，不能改别人的等级。
- 第三级新建账号时选定第二级或第三级，并为这个新账号设置用户名和口令。口令沿用现有规则：至少 10 位，且不在现有弱口令表里。
- 新账号放进创建者当前所在的工作区，成员角色为 `VIEWER`。

## 3. 额度怎么计

额度按人计，不按工作区。同一个人在哪个工作区提问，都扣这个人自己的额度。

一天从上海时间晚上 12 点开始，到下一个晚上 12 点结束。到点后已用清零，当天如果加过的 50 万也清掉，上限回到上表里的等级原值。

计入额度的 Token：

- 这一问里每次大模型调用的输入 Token 加输出 Token；
- 为了回答这一问而做的检索向量化，送出去的文本 Token。算在提问的人头上，和这一句的其他步骤加在一起。

不计入：

- 被每秒次数拦住、因而没有开始的那一次。
- 开跑前判定为余额不够、因而一个字都没跑的那一次。
- 把文档上传到知识库时的解析、分块和向量化。这不扣上传者的个人额度，也不扣其他人的额度。
- 程序启动时写入意图示例。这次没有对应的用户。

现网缺口，本版必须补上，否则进度条和「哪一句最多」都会偏：

- 流式回答现在把 Token 记成 0。本版要记下服务商返回的用量。
- 一次运行结束时，运行记录上的 Token 合计现在也写成 0。本版以该次运行下面各次调用的合计为准，供「哪一句最多」使用。
- 提问时的检索向量化现在不进这张账。本版要计入。服务商返回了用量就用那个数；没返回就用和开跑前同一套本地计数，数的是这次送去向量化的文本。上传文档和启动写入意图示例仍然不进个人额度。

开跑前的预估不调用模型。只数用户刚发出的那句原文，加上这条会话里近期对话的原文。近期对话的条数与现有改写所用的近期窗口相同（近 20 条消息）。第一句没有历史，就只数这一句。

## 4. 提问时发生什么

用户按一次发送，每秒最多 2 次。三个等级同一个数。这一次包含聊天页先做的意图预检、流式问答、复合问题，以及数据分析。不能只守住其中两个地址，让另一次调用把模型和向量花掉。同一句里面的改写、意图、检索、生成 SQL，以及复合问题拆出来的子问题，都算这一次，Token 加在同一个人头上。超过时不调用模型，页面只说「请求过于频繁，请稍后再试」，不出现提额入口。这是防脚本刷接口，不写进「今日额度」，提额也不提高它。

没被每秒次数拦住时，用第 3 节的预估和这个人今天的剩余额度比：

- 剩余额度小于预估：一个字都不出。不跑意图识别、查询改写、检索和查数。
- 第一级、第二级看到：「今日 Token 额度不足，请提额后再问。」并可以去提额。
- 第三级看到额度用完，没有提额入口，也不能提交提额。
- 剩余额度够付这段预估：才开始执行。这一问一旦开始，里面的改写、意图、检索、生成 SQL、回答，以及复合问题拆出的子问题，都做完。不因为中间某一步记完后剩余为 0，就停掉后面的字或后面的步骤。
- 每一步在该步调用结束时记账。流式回答的用量在这段话说完、服务商带回用量时记下。这一问可以略微超出当时剩下的额度，超出的部分照记，不退回。
- 这一问记账之后剩余不足：下一句才拦住。下一句若开跑前预估超过剩余，仍是一个字都不出。

进度条放在聊天输入框下面、发送按钮上面，靠左，不占满整行。标题是「今日额度」。旁边写剩余百分比。剩余百分比 = 剩余 Token / 当天上限。剩余小于 0 时，百分比按 0 显示。进度在这一问记账之后更新，不按已经吐出的字逐字变动。提额通过后，当天上限变成等级原值加 50 万，百分比按新上限重算。

## 5. 提额

只加 Token，不加每秒次数。通过后，申请人当天上限加 50 万。只在当天有效。

谁向谁申请：

- 第一级向第二级申请。本版第二级就是 `limit`。
- 第二级向第三级申请。本版第三级就是 `blank`。以后若有多名第三级，这些第三级都可以审。
- 第三级不能提额。

申请不消耗 Token。额度已经用完也可以打开申请页。

申请页列出这个人今天已经记下 Token 的每一句，以及这一句的 Token 数。系统标出最多的那一句。用户确认后，这句话和它的 Token 数写入申请理由。用户不填写内部步骤。系统把这一句里面 Token 最多的那一次调用的步骤名和 Token 数附在申请上，只有审评的人能看见。

没跑起来的句子没有消耗，不出现在这张列表里。还没写上用量的那一步不参与比较。列表在每次打开或再次提交时按当时的账重算。

审评：

- 未通过：可以再提交。
- 通过：当天不能再提交。晚上 12 点之后，这一天的「已通过」失效，下一天可以再成功一次。
- 通过之前可以有多次未通过的提交。一天里成功只有一次。

提额通过的瞬间不自动开跑。已经说完的那一问保持原样。用户要再问，就新发一句，按新的剩余额度做开跑前检查。

## 6. 数据

新增用户等级，取值 1、2、3。不要复用 `workspace_members.role_code`。

新增提额申请：申请人、审评人、状态（待审、通过、拒绝）、申请理由、系统附上的步骤名和该步骤 Token、这一天的日期、创建时间、审评时间。

每天已用可以从现有调用记录按人、按上海时间的日期加总，不必为了进度条再抄一份总账。提额通过后的额外 50 万记在当天的额度调整上，晚上 12 点不再计入上限。

Flyway 接在现有 V13 之后。不改 V1–V13，也不把这条迁移算进 v1.4.0。

## 7. 实施时自行决定的部分

- 本地 Token 计数用哪一个分词实现。它必须稳定、不发起模型请求，并且开跑前预估和向量化缺用量时的回退用同一种数法。
- 流式响应里从哪一个字段读取服务商用量。读不到则这一段记 0，并在日志里留一句，避免再静默写成成功的 0。
- 审评页的版式。必须能看见申请人、申请理由、系统附上的步骤和 Token，以及通过、拒绝。不要求和聊天页同一套视觉稿。
- 第三级创建账号的表单字段，除用户名、口令、等级（只能选 2 或 3）外，显示名可空。

## 8. 验收

- 新注册用户是第一级，每天上限 50 万。`blank` 是第三级，`limit` 是第二级。两人的工作区角色仍是 `VIEWER`。
- 不能把一个第一级用户改成第二级或第三级。第三级可以新建第二级或第三级账号。第二级不能新建账号。
- 甲用完自己的额度时，乙的剩余百分比不变。
- 预估超过剩余额度时，回答区没有正文，数据库里没有这一问的改写或意图步骤。
- 开跑前预估够、这一问已经开始后，回答会说完。记账后即使剩余不足，这一问的正文也完整留在页面上。下一句才被拦住。
- 「今日额度」在输入框与发送按钮之间，靠左，带剩余百分比。
- 第一级的申请由 `limit` 审。第二级的申请由第三级审。第三级没有提额入口。
- 拒绝后可以再交。通过后当天不能再交，上限增加 50 万。上海时间晚上 12 点后上限回到等级原值。
- 提问时的检索向量化出现在这个人当天的已用里。上传文档到知识库不改变任何人的已用。
- 同一用户一秒钟内第 3 次发问得到「请求过于频繁，请稍后再试」，并且没有提额入口。
- v1.4.0 规格第 14 节的验收项不因本版而改写。
